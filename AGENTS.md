# Library boundaries

Docture publishes exactly three packages: `docture`, `@docture/cli`, and `@docture/eval`. The decisions and migration tradeoffs are recorded in [the package architecture decision](docs/decisions/0001-package-boundaries.md) and [the eval publication decision](docs/decisions/0002-eval-publication.md).

- Keep `docture` ESM with per-file output, explicit subpath exports, and audited `sideEffects: false` metadata. Do not bundle each entry into a separate copy of core.
- Keep the root entry limited to core. Core must not import LLM implementations, adapters, testing tools, or optional engines, including through type declarations.
- Use relative imports inside the runtime package so all entries in one install share the same core modules. A process can still load several installed copies (pnpm installs one per peer set), so every `DoctureError` subclass declares its own `doctureErrorIdentity`. Never recognize errors by constructor name, `name`, or `code` alone. Type a parameter that accepts objects from another copy, such as a CLI config field, by the methods it calls rather than by a class with private fields.
- Keep integrations isolated. Reserve `node:module` asset resolution for the adapter modules declared in the boundary check. Add a narrow entry for each independent capability. Do not import a registry or convenience facade from a narrow entry. Give every LLM module a role in the boundary check: helpers stay engine-free, capabilities import only helpers and shared modules, and only the extractor factory and convenience modules combine capabilities. Preserve convenience APIs, but document that a used class can retain its referenced methods and dependencies.
- Declare optional integration engines as optional peers. Install them explicitly in development and in consumer recipes. Normal optional dependencies install by default; reserve them for deliberate CLI defaults. Keep development versions exact. Declare an engine range only after the packed gate verifies its floor and newest release, recorded in its engine matrix; otherwise keep the exact pin. When an engine loads another engine itself, as PDF.js loads `@napi-rs/canvas`, list the pair in the gate's `coupledEngines`, start the dependent range inside every supported version's own requirement, and use objects that the loading engine creates, not ones from a separately imported copy. Load lazy engines through `importEngine` so an absent peer raises `MissingEngineError`, and keep `ENGINE_RANGES` equal to the declared ranges.
- Keep module imports free of observable startup work. Load native, WASM, OCR models, and PDF workers when the selected integration is used. A new side effect requires revisiting the package metadata and bundle tests.
- Update the documentation import paths, engine install recipes, API coverage inventory, and executable examples when the public surface changes. Test names describe behavior rather than tickets or migration phases.

Run `pnpm lint` for import boundaries. Run `pnpm verify:packages` after entry-point, dependency, build, or integration changes. This packs and installs the real packages outside the workspace and checks Node, types, optional engines, class identity, and production bundle isolation. Do not replace these checks with workspace-only imports or a bundle-size claim.

Before handing off a library change, run `pnpm typecheck`, `pnpm test`, and `pnpm build`, plus relevant runnable examples. Model calls requiring credentials are covered by deterministic provider mocks; report any live checks that were not run. Follow the additional instructions in `apps/docs/AGENTS.md` when working on the documentation app.
