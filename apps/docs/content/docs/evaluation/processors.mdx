A processor is the code under test: it receives a case and returns raw output for scoring. Wrap a Docture extractor or your own code as a processor.

## Adapt an extractor

Use `fromDocture` to evaluate an existing extractor and contract:

```ts
import { fromDocture } from "@docture/eval/docture";

const processor = fromDocture(extractor, Invoice, { id: "invoice-parser" });
```

Each case must contain one non-empty document. The runner calls the processor and disposes its extractor at the end. Construct a fresh extractor for another independent run.

## Write a custom processor

A custom processor needs `id` and `extract(item, context)`. Return `{ raw }`; add `usage`, `confidence`, `evidence`, `method`, or `fallback` when measured. The runner accepts a structural object, so your processor needs no Docture base class.

These records serve different purposes:

| Field | Owner | Shape |
| --- | --- | --- |
| `expected` | Dataset case | The approved comparable value. |
| `locations` | Dataset case | A record keyed by expected field path, with an array of page and optional box locations. |
| `confidence` | Processor output | A record keyed by actual field path, with a number in `[0, 1]` for each reported confidence. |
| `evidence` | Processor output | A `FieldEvidence[]` array. Each entry has its own `path`, one-based `pageNumber`, and optional `box`. |

Use concrete paths such as `items[0].amount`. The runner's array alignment connects actual paths to their expected counterparts.

## Run a processor with confidence and evidence

Use Node.js 22 or newer. Install the evaluator and script runner:

```sh
npm install @docture/eval docture zod@^4.1.8
npm install --save-dev tsx
```

Save this program as `evaluation-analysis.mts`. It reads two recorded page fixtures with text, confidence, and a source box. The fixture confidence is fixed at `0.9`; it demonstrates how to pass a recorded signal through the processor without treating that signal as correctness.

<SourceExample file="evaluation-analysis.ts" title="evaluation-analysis.mts" />

Run it:

```sh
npx tsx evaluation-analysis.mts
```

The program prints:

```txt
F1 0.5
Confidence [{"confidence":0.9,"count":2,"correct":1}]
Auto-accept threshold null
Grounded F1 0.5
Gate passed false
```

The parser accepts `Subtotal cents` before the final `Total cents` in the credit case, returning `200` instead of the printed, approved `190`. Its evidence points to the subtotal row. Both answers carry confidence and source evidence, but only one value is correct and grounded. Two observations cannot support the default auto-accept precision bound, so the threshold is `null`.

The script asserts this failed quality gate and exits successfully when the demonstration behaves as expected. A CI job that requires the quality gate to pass must fail when `accepted.pass` is false. The exported `evaluateBills()` function lets the [calibration](/docs/evaluation/calibration) and [grounding](/docs/evaluation/grounding) guides reuse these cases.

## Preserve raw output for later scoring

Use `project(raw)` when processor output differs from the expected scoring view. The runner stores raw output, so a saved run can be re-scored with a new projection. Put settings that change extraction in the processor's serializable `config` so resume detects the change.

## Handle setup, cleanup, and failures

`preflight` prepares a processor before work. `dispose` releases it after success, failure, or cancellation. Honor `context.signal` in external operations. Throw `OutOfScopeError` only for deliberately excluded inputs. Other failures produce errored cases; valid failure `usage` still contributes cost and tokens.

Docture failures become errors, including unsupported sources. `fromDocture` does not invent a scope policy or model-call count. It can price successful and failed attempts when given matching pricing settings.

See [adapter API](/docs/evaluation/reference/processors), [runner API](/docs/evaluation/reference/runner), and [experiments](/docs/evaluation/experiments).
