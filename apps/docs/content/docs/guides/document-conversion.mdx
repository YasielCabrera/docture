title: Convert documents
description: Recover grounded PDF text and layout as TXT, Markdown, HTML, or versioned JSON.
---

`DocumentConverter` turns the same loaded document used for extraction into indexable
text, Markdown, HTML, or versioned JSON. It does not ask for a schema and it does not paraphrase source
text. The example writes `converted/report.md` and any referenced assets.

<SourceExample file="document-conversion.ts" title="convert-document.ts" />

The default format is Markdown. The default asset mode is `referenced`, so image bytes
stay in `result.assets` and the Markdown points at stable relative names.

## Install

```sh
npm install docture pdfjs-dist@6.2.108 zod@^4
```

See [installation recipes](/docs/guides/installation) for other engines and providers.

## Digital and scanned PDFs

A PDF with a text layer needs only a PDF loader:

```ts
const converter = new DocumentConverter()
  .loadDocumentLoader(new DocumentLoaderPdfJs());

const result = await converter.convert("report.pdf");
```

The default CLI loader is also PDF.js. A scanned PDF has no text layer, so PDF.js returns
no convertible content and conversion throws `NoConvertibleContentError`. Configure an
OCR loader explicitly when scans are expected:

```sh
npm install docture zod@^4 tesseract.js@7.0.0 pdfjs-dist@6.2.108 @napi-rs/canvas@1.0.10
```

```ts
import { DocumentLoaderTesseract } from "docture/loaders/tesseract";
import { NapiCanvasRasterizer } from "docture/raster/canvas";

const converter = new DocumentConverter()
  .loadDocumentLoader(new DocumentLoaderTesseract({
    rasterizer: new NapiCanvasRasterizer({ dpi: 300 }),
    languages: ["eng"],
  }));
```

Tesseract reads image files directly. The rasterizer in this example is what lets the
same OCR loader accept PDF input.

Conversion does not switch loaders or OCR modes after a loader succeeds. This keeps the
loader choice, cost, and recovered text visible.

## Selected pages

Pass `pages` to convert part of a document. PDF loaders read only those pages, and the
result keeps their original numbers:

```ts
const result = await converter.convert("report.pdf", { format: "json", pages: [2, 3] });
result.pages.map((page) => page.pageNumber); // [2, 3]
```

Running headers and table continuations are detected among the selected pages only. An
element that lies wholly on a selected page keeps its ID unless that detection changes
its kind or rows.

## Output formats

```ts
await converter.convert(source, { format: "text" });
await converter.convert(source, { format: "markdown" });
await converter.convert(source, { format: "html" });
await converter.convert(source, { format: "json" });
```

- TXT joins pages with form feeds and adds no image placeholders.
- Markdown uses CommonMark, GFM tables, and `<!-- page: N -->` markers.
- HTML is a complete escaped HTML5 document. Each page is a numbered `section`.
- JSON exports the versioned `DoctureDocument` with semantic elements, provenance, and assets.

All four formats read the same semantic elements. Headings, paragraphs, lists, tables,
code, figures, page breaks, and running headers and footers retain page and bounding-box
provenance.

## Assets

`assets` accepts `referenced`, `embedded`, or `omit`:

```ts
const referenced = await converter.convert(source, { assets: "referenced" });
const embedded = await converter.convert(source, { assets: "embedded" });
const textOnly = await converter.convert(source, { assets: "omit" });
```

Referenced output uses stable relative names such as
`report.assets/page-1-image-1.png`. `result.assets` carries each name, media type,
position, and `Uint8Array` value. Embedded Markdown and HTML use data URLs. Omit mode
does not ask the loader for asset bytes.

V1 copies embedded raster figures. It does not reconstruct vector art or produce a
pixel-matched HTML rendering of the page.

## Deterministic and model-assisted layout

Core first applies deterministic reading-order and structure rules using tagged hints,
geometry, and typography. Uncertain structures remain paragraphs. It does not
dehyphenate text, generate captions, or change substantive characters.

## Running headers and footers

Core marks running headers and footers as `page-header` and `page-footer` elements.
Markdown and HTML leave them out of the body, so chunks built from that output do not
repeat a company name or page number per page. TXT and JSON keep them, in place at the
top and bottom of each page.

```ts
const result = await converter.convert(source, { format: "markdown" });
const footers = result.pages.flatMap((page) =>
  page.elements.filter((element) => element.kind === "page-footer"),
);
console.log(footers.map((footer) => footer.text)); // ["Page 1 of 3", ...]
```

A tagged PDF's `header` and `footer` hints count when the line sits in the top or bottom
10% of the page. Without tags, core infers furniture from text that repeats in those bands
on at least three pages, including odd-page and even-page running heads. Page numbers
match when they follow the page. These thresholds are heuristics. A one-page or two-page
document gets furniture only from tags. A page number such as `Page 2 of 6` can sit up to
15% from the top or bottom when it follows the pages, keeps the same height and indent, and
has a line of blank space between it and the body. Bold text there, such as a numbered
`Question 1` heading, stays in the body. Other text lower than 10% of the page
stays in the body. A band line that repeats at the same place on another page without meeting these
rules, such as a running header on a two-page document, also stays in the body. It is never
a table row, and a table does not continue across it. The [reference](/docs/reference/api/core-conversion#semantic-layout) lists the
rules.

Optional model assistance can refine roles and ordering:

```sh
npm install docture pdfjs-dist@6.2.108 ai@^7 @ai-sdk/openai zod@^4
```

```ts
import { LLM } from "docture/llm";
import { openai } from "@ai-sdk/openai";

const converter = new DocumentConverter()
  .loadDocumentLoader(new DocumentLoaderPdfJs())
  .loadLlm(new LLM(openai("gpt-5")));
```

The model response schema contains element IDs, roles, levels, and order only. It has no
text field. The model never sees page headers and footers. Core rejects unknown IDs,
duplicate IDs, and invalid order permutations. A
failed or invalid response leaves deterministic conversion in place and adds a warning
and failed attempt.

## Tables and merged cells

Core groups aligned rows into `table` elements. Rows with the same number of cells at
matching positions form a plain table. When rows differ in cell count, the rows with the
most cells set the column bands. A shorter row joins the table when each of its cells
falls in a band, so a totals row stays with its table. A row more than 1.5 times the row
spacing below the row above starts a new form section instead, unless it holds a number
without letters in the table's last column, as a totals row does. That holds for a shorter row, such as
`Booking ID` and `Payment Mode` labels under a `Check In`/`Check Out`/`Rooms` table, and
for a row in a different font weight. The section and the rows above it become tables
only if each is a table on its own. A label over two columns becomes
a merged cell:

```ts
const result = await converter.convert(source, { format: "json" });
const table = result.pages[0]?.elements.find((element) => element.kind === "table");
console.log(table?.rows); // [["Item", "Quarters", ""], ["", "Q1", "Q2"], ["Alpha", "10", "20"]]
console.log(table?.headerRows); // 2
console.log(table?.spans); // [{ row: 0, col: 1, rowSpan: 1, colSpan: 2 }]
```

`rows` keeps one slot per column. A merged cell's text is in its anchor slot, and every
slot it covers holds `""`. Each format renders spans differently:

- HTML puts the `headerRows` rows in `<thead>` and writes `colspan` and `rowspan` on the
  anchor cell.
- Markdown has no merged cells. It flattens the header rows into one row and joins each
  column's labels with ` / `, as in `| Item | Quarters / Q1 | Quarters / Q2 |`. Covered
  body cells stay blank, so a value is never copied into another cell.
- TXT keeps the original source lines.
- JSON keeps `rows`, `headerRows`, and `spans`.

Detection is a heuristic. A label must cover more than half of each column it merges,
and those columns must be empty in its row. A bold label in a bold header row can instead
sit centred over two or more columns, such as `Quarters` above `Q1` and `Q2`, even when it
overlaps neither. A centred line without bold type stays outside the table with a
`LAYOUT_DEGRADED` warning, because it could also be a caption. A caption such as
`Table 1` or `Table A`, heading-size text, or a line more than 1.5 row spacings above the table never
merges. Rows above the band rows join only as header
rows that a merged label proves. A row span needs a cell box that covers at least half of
each row line, which OCR or synthetic geometry can provide and PDF text layers rarely do.
An empty cell never makes a row span. Text layers that emit one span per word keep the
plain table rule. A layout analyzer group that would produce an invalid table is
ignored, and the tables stay separate. The
[reference](/docs/reference/api/core-conversion#semantic-layout) lists the rules.

## Tables and paragraphs across pages

A table that runs over a page break becomes one table, and so does a paragraph cut
mid-sentence. The joined element lives on the page where it starts. Its provenance keeps
one segment per page, and a table keeps one `rowProvenance` entry per row:

```ts
import { provenanceSegments } from "docture";

const result = await converter.convert(source, { format: "json" });
const table = result.pages[0]?.elements.find((element) => element.kind === "table");
if (table?.kind === "table") {
  console.log(provenanceSegments(table.provenance).map((segment) => segment.pageNumber)); // [1, 2]
  console.log(table.rowProvenance?.map((segment) => segment.pageNumber)); // [1, 1, 1, 2, 2, 2]
}
```

Each `ConvertedPage` holds the elements that start on it, so page 1's content includes the
rows from page 2, and page 2 omits them. Every format renders a joined element once, on its
starting page. The next page's `<!-- page: N -->` marker, HTML `section`, or TXT form feed
follows the whole element. TXT stays in page order but is no longer exact per physical
page. A footer line of page 1 that is not detected as furniture prints after the joined
text.

Joining is a heuristic, and it keeps elements apart when the evidence is weak. A table or
paragraph joins only when it ends in the bottom quarter of its page and the next page's
first element starts in that page's top quarter. A table continues with rows that have the
table's cell count, the same font size and weight, cells of at most 40 characters, and cells
inside the table's columns. In a column whose body cells on the earlier page are all
numbers without letters, a continued row must have no letters there. An unrelated table, a
key-value block, or two-column prose in the table's columns therefore starts a new element
when the table has such a column. A table without such a column holds only text, and matching
columns are no evidence that the next page continues it. Its rows join only after a copy of
its header row, or under a line such as `Table 4 (continued)` when `Table 4: Staff`, or
another `Table 4` caption, sits right above the table. Such a line counts even when it
repeats at the top of every page, and it is never a running header. A line for another
table, such as `Table 5 (continued)`, keeps the rows apart. Otherwise the rows stay on their page
with a `LAYOUT_DEGRADED` warning. A bold or heading-size line set apart at the top of the next
page starts a new section, unless it is a copy of the header row, so a header copy below a
section title starts a new table. After a continued row, a totals row with fewer cells
joins when its cells fall in the table's columns. A later row with the full cell count
meets every check above, so a bold header further down starts a new table. Every row after the first must start
within three times the table's row spacing of the row above, so a footer or signature line
lower on the page stays out. A copy of the header row at the top of the next page is
dropped from `rows` and kept in `sourceText`. A row in a different font weight, or rows in
other columns, start a new element. A paragraph continues when it does not end with `.`,
`!`, `?`, `:`, or `;`, and the next page's first element starts with a lowercase letter.
Text in scripts without letter case therefore never joins. A contents or index entry on
either side of the break never joins. Such an entry ends in an Arabic or Roman page number
after a dot leader, such as `Contents .......... 7`, or after a gap of at least two line
heights. A final number after an ordinary word space is body text. Page furniture, and a top or
bottom line that blank space sets apart from the body, are skipped. A line that repeats at the
same place on another page but is not furniture is not skipped: the table and the next page's
rows stay apart, and the result carries a `LAYOUT_DEGRADED` warning that names both lines.
Text-only pages never join.

Some layouts still join wrongly:

- A line at the bottom of a page that ends without punctuation, such as a list entry, joins
  a paragraph that starts with a lowercase letter at the top of the next page. A layout analyzer can reorder a joined element's page, but the
element stays last in its page's text, and annotations that would retype or group it are
ignored.

## Serverless and in-memory use

The library never writes files:

```ts
const result = await converter.convert(pdfBytes, {
  format: "html",
  assets: "embedded",
});

return new Response(result.content, {
  headers: { "content-type": result.mimeType },
});
```

This works in a request handler, queue worker, or indexing job without a temporary output
directory. Chunking, embeddings, and index writes remain application concerns.

## Result provenance

`ConversionResult` contains whole-document `content`, MIME type, page fragments,
semantic elements, in-memory assets, loader and method names, document features,
attempts, warnings, model usage, and wall time.

```ts
for (const page of result.pages) {
  for (const element of page.elements) {
    console.log(element.kind, element.provenance.pageNumber, element.provenance.box);
  }
}
```

Use `safeConvert()` for a non-throwing result and `convertBatch()` for bounded parallel
conversion. Call `dispose()` when the converter owns loaders or a model analyzer.

## CLI

```sh
npm install --save-dev @docture/cli
```

The CLI always requires an output directory:

```sh
docture convert reports/*.pdf --out converted/
docture convert report.pdf -o converted/ --to html --assets embedded
docture convert report.pdf -o converted/ --assist-layout --model openai/gpt-5
```

It writes `<out>/<stem>.md`, `.html`, `.txt`, or `.json`. Referenced assets go under
`<out>/<stem>.assets/`. Basename collisions are rejected before any document is loaded.
In a batch, successful outputs remain on disk if another input fails, and the process
returns exit code `1`.

## Export structured JSON

`format: "json"` returns a version 2 document with page dimensions, semantic elements,
provenance, assets, and warnings. The CLI writes it with `docture convert report.pdf
--out converted --to json`. `--format json` separately selects the command envelope.
See the [JSON format reference](/docs/reference/api/core-conversion#versioned-json) and
the [generated schema](/schemas/docture-document-v2.schema.json).

Validate a saved file before you use it. `parseDoctureDocument()` accepts version 1 and
version 2 files and returns version 2:

```ts
import { readFile } from "node:fs/promises";
import { parseDoctureDocument } from "docture";

const parsed = parseDoctureDocument(JSON.parse(await readFile("converted/report.json", "utf8")));
if (!parsed.ok) throw new Error(parsed.issues.map((issue) => issue.path + ": " + issue.message).join("\n"));
```

To see the elements over the pages they came from, run `docture review --conversion
converted/report.json --source report.pdf`. See [Review](/docs/guides/cli#review).
