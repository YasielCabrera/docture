---
title: Concurrency and memory
description: Choose batch, model request, OCR, and raster settings from measured throughput and memory.
---

Docture has several independent concurrency controls. Some run work in parallel on
several CPU cores. Others only overlap waiting, such as model requests and file reads.
This page lists each control, shows which work stays on the main JavaScript thread, and
gives measurements you can reproduce on your own machine.

## Controls and defaults

| Work | Option | Default | What runs at once |
| --- | --- | --- | --- |
| Documents in a batch | `concurrency` on `extractBatch()`, `convertBatch()`, and bundle extraction | `4` | Whole documents. Each one loads, then runs its strategies. |
| Documents in the CLI | `--concurrency <n>` or `concurrency` in `docture.config.ts` | `4` | Inputs of `extract`, `convert`, `classify`, and `eval`. The flag accepts 1 to 64. |
| Text chunks of one document | `llm({ concurrency })` | `4` | Model requests for one document's chunks or pages. |
| Vision requests of one document | `vision({ concurrency })` | `4` | Model requests, each with up to `pagesPerRequest` images (default `20`, or one with `pageMode: "perPage"`). |
| Lazy bundle seams | `concurrency` on `runSplitter()` | `4` | Model checks of adjacent page pairs under `SplittingStrategy.LAZY`. |
| Tesseract pages | `DocumentLoaderTesseract({ concurrency })` | `max(1, min(4, availableParallelism() - 1))` | Worker threads, each with its own WASM engine and model. |
| PaddleOCR pages | `DocumentLoaderPaddleOcr({ concurrency })` | `"auto"`: `4` with CPU execution providers, `1` when any accelerator provider is listed | Pages in flight against one shared pair of ONNX sessions. |
| Render resolution | `dpi` on rasterizers and OCR loaders | `300`; `vision()` uses `200` | Not a concurrency control. Pixel count grows with the square of DPI. |
| Image edge limit | `maxEdge` | none on rasterizers; `1568` in `vision()` | Not a concurrency control. Caps the longer image edge after DPI. |

The two OCR defaults are different controls. Tesseract reads the CPU count and starts
up to that many worker threads, so it does real parallel work. PaddleOCR's `"auto"` does
not read the CPU count. It picks `4` or `1` from the execution providers, and all pages
share the same two ONNX sessions.

## Composed controls multiply

Controls at different levels multiply. `extractBatch()` with `concurrency: 4` and
`llm({ concurrency: 4 })` can keep 16 model requests in flight. Size the product to your
provider's rate limit, not each control on its own.

OCR pools belong to a loader instance. A Tesseract loader creates its worker pool on its
first load, sized by the loader's `concurrency`, and reuses it for every later load.
Concurrent documents on the same loader queue for those workers, so a batch of four
documents still uses at most the pool's workers. A PaddleOCR loader also builds one
engine and reuses it, but each concurrent document runs its own page pool against it.
Four documents with `"auto"` can have 16 page images in flight on one engine.

## Work on the main thread

`--concurrency` and `extractBatch()` concurrency overlap model calls and file or network
I/O. They do not make CPU-bound work parallel. The [CLI guide](/docs/guides/cli) ends
with the same caveat for `--concurrency`, and [loaders](/docs/concepts/loaders#selection-and-failures)
describe it for PDF.js and MuPDF.

These steps run on the main JavaScript thread:

- PDF.js text extraction and page rendering, including `NapiCanvasRasterizer` drawing and
  PNG encoding.
- MuPDF parsing and rendering. It yields between pages, but each engine call blocks.
- PaddleOCR image preprocessing and inference. onnxruntime-node 1.27.0 calls the native
  session synchronously from the main thread. The ONNX runtime spreads one inference over
  several cores, but two pages do not run inference at the same time.
- Rendering the pages that an OCR loader reads. Tesseract and PaddleOCR render all of
  those pages before recognition starts.

Tesseract recognition runs in worker threads. Model requests are network I/O and wait
off the thread. To keep a server responsive during CPU-bound work, run docture in a
`worker_threads` worker or a separate process.

## Measured results

The checked-in benchmark creates its own PDFs with `docture/testing/fixtures`, so it needs
no corpus download. Run it from the repository root after `pnpm install` and `pnpm build`:

```sh
pnpm --filter @docture/examples exec node benchmarks/concurrency.ts --reps 5
```

It prints its conditions first, then one row per scenario and variant. Each run is a
fresh Node process. Cold time includes engine setup in that process. Warm time repeats the
same work with the same objects. Max RSS is the whole process, worker threads included.
Variants alternate within each repetition, after one discarded round. The units column
counts the work the warm pass completed: correct batch results, model requests, OCR pages
with recognised text, or rendered pages. Errors count every intended unit that either pass
did not complete. The script exits with status 1 when a run completed less than intended.

Conditions for the numbers below:

- Command: `pnpm --filter @docture/examples exec node benchmarks/concurrency.ts --reps 5 --json`.
- docture 0.2.0 from the workspace build, Node 24.14.0, pdfjs-dist 6.2.108,
  @napi-rs/canvas 1.0.10, tesseract.js 7.0.0, ppu-paddle-ocr 6.3.0, onnxruntime-node
  1.27.0, ai 7.0.51.
- Apple M4 Max, 14 logical CPUs, 36 GiB RAM, macOS (Darwin 25.6.0). Load average 2.46 at
  start and 5.04 at the end (1 minute). A background virtual machine used about a third of
  one core. No other benchmark or build ran at the same time.
- 5 runs per variant, reported as median with the range in parentheses. 0 errors in every
  row.
- Inputs: eight one-page invoices for batches, one 8-page invoice for chunks, vision, and
  rendering, and one 4-page invoice for OCR. OCR models were already in the local cache.

### Model requests, controlled mock provider

These rows use a deterministic mock model, not a real provider. It answers every request
after a fixed 100 ms. They measure how docture schedules requests. They say nothing about
a provider's latency or rate limits.

| Scenario | Concurrency | Warm time (s) | Throughput | Max RSS (MiB) |
| --- | --- | --- | --- | --- |
| `extractBatch()`, 8 documents | 1 | 0.91 (0.90-0.92) | 8.8 documents/s | 217 (217-221) |
| `extractBatch()`, 8 documents | 4, default | 0.25 (0.24-0.25) | 32.6 documents/s | 234 (220-237) |
| `llm()` pages, 8 requests | 1 | 0.87 (0.86-0.88) | 9.2 pages/s | 210 (209-210) |
| `llm()` pages, 8 requests | 4, default | 0.25 (0.24-0.25) | 32.1 pages/s | 210 (210-212) |
| `vision()` per page, 8 requests | 1 | 1.30 (1.27-1.30) | 6.2 pages/s | 257 (240-267) |
| `vision()` per page, 8 requests | 4, default | 0.47 (0.47-0.48) | 17.0 pages/s | 316 (292-342) |

The mock latency limits the text rows. Eight requests take 0.8 s one at a time and 0.2 s
in two groups of four, and parsing adds the rest. Vision gains less, 2.8 times instead of
3.5 times, because each page is rendered on the main thread at 200 DPI with the 1568 pixel
edge limit before its request. With concurrency 4 the process used 0.9 CPU cores, which
is one thread doing the rendering while requests wait.

### OCR

| Loader | Concurrency | Cold time (s) | Warm time (s) | Throughput | CPU cores | Max RSS (MiB) |
| --- | --- | --- | --- | --- | --- | --- |
| Tesseract, 300 DPI | 1 | 6.77 (6.66-6.89) | 6.31 (6.22-6.34) | 0.63 pages/s | 1.0 | 622 (618-623) |
| Tesseract, 300 DPI | default, 4 workers here | 2.64 (2.62-2.65) | 2.18 (2.16-2.27) | 1.83 pages/s | 3.1 | 1248 (1244-1257) |
| PaddleOCR, 300 DPI | 1 | 2.18 (2.14-2.25) | 1.68 (1.67-1.71) | 2.38 pages/s | 4.5 | 2235 (2222-2261) |
| PaddleOCR, 300 DPI | `"auto"`, 4 on CPU | 2.20 (2.16-2.27) | 1.70 (1.67-1.77) | 2.36 pages/s | 4.5 | 2538 (2519-2574) |

Tesseract's default pool was 2.9 times faster than one worker on this machine and used
about 210 MiB more memory per extra worker. It is not 4 times faster because the four
pages are rendered on the main thread before any worker starts. The rendering table puts
that at about 0.65 s for four pages at 300 DPI.

PaddleOCR `"auto"` showed no measurable speedup over `concurrency: 1`; the ranges overlap.
Both used about 4.5 cores, which is the ONNX runtime's own threads inside one inference.
Extra pages in flight only held more decoded images, about 300 MiB here. Measure your own
documents and execution provider before you raise it, and consider `concurrency: 1` when
memory is tight.

The cold column adds about 0.5 s for each loader. That is worker or session startup and
model loading from the disk cache. A first run on a new machine also downloads models.

### Rendering

`NapiCanvasRasterizer.rasterize()` over all 8 pages, PNG:

| Options | Page size (px) | Total PNG | Warm time (s) | Throughput | Max RSS (MiB) |
| --- | --- | --- | --- | --- | --- |
| `dpi: 150` | 1240 x 1753 | 2.3 MiB | 0.40 (0.40-0.42) | 19.8 pages/s | 328 (327-330) |
| `dpi: 300` | 2480 x 3507 | 5.1 MiB | 1.31 (1.30-1.43) | 6.1 pages/s | 532 (526-541) |
| `dpi: 300, maxEdge: 1568` | 1108 x 1568 | 2.0 MiB | 0.34 (0.34-0.36) | 23.4 pages/s | 303 (300-327) |

Doubling DPI quadruples the pixels. Render time grew 3.3 times. Every row used one core,
because rendering is single-threaded. `maxEdge` is applied before drawing, so a 300 DPI
request with `maxEdge: 1568` costs less than a 150 DPI render.

## Memory controls

- OCR loaders hold an encoded PNG of every page they read until recognition ends. Pass
  `pages` to `extract()` or `convert()` to render only those pages. `maxPages` limits
  recognition but does not skip rendering a PDF.
- `page.image()` memoizes one render per page and raster options. A second call with the
  same options reuses it. Different `dpi` or `maxEdge` values render again.
- TIFF input is bounded per page: at most 8192 x 8192 pixels and 256 MiB of decoded
  samples. PaddleOCR converts a TIFF page to PNG in bands of rows instead of one full RGBA
  copy. These limits are not part of the benchmark above.
- Each Tesseract worker keeps its own engine and model. Lower `concurrency` before you
  lower `dpi` when memory is the limit, because `dpi` also changes accuracy.

## Choose settings

1. For model-bound work, raise batch or request concurrency to your provider's rate limit.
   Count the product of the levels.
2. For Tesseract, keep the default unless memory is tight. Expect about 200 MiB per
   worker at 300 DPI.
3. For PaddleOCR on CPU, measure `concurrency: 1` against `"auto"` with your documents.
4. For vision, keep the default `maxEdge: 1568` or set your provider's limit. It cuts
   render time and request size.
5. Run the benchmark with `--only model`, `--only ocr`, or `--only raster` to compare
   one group on your hardware.
