`docture/loaders/docling` connects to a running docling-serve instance over HTTP. It needs no npm peer, Python process, local OCR engine, or model. Use `DoclingServeClient` for direct conversions and jobs, or `DocumentLoaderDoclingServe` inside an extractor or converter.

## Prepare the service

Before running the client:

1. Start a Docling Serve instance using the [official 1.38.2 setup guide](https://github.com/docling-project/docling-serve/blob/v1.38.2/README.md#getting-started), the protocol release covered by the adapter fixtures.
2. Record its service root and any API key required by your deployment.
3. Choose a PDF, DOCX, XLSX, PPTX, or EPUB file that the service can read.

The server needs its own engines and model assets. Docture does not install or start them.

## Convert a document

Run this complete client example beside `invoice.pdf`:

```ts check
import { readFile } from "node:fs/promises";
import type { RawDocument } from "docture";
import { DoclingServeClient } from "docture/loaders/docling";

const client = new DoclingServeClient({ baseUrl: "http://127.0.0.1:5001/" });
const rawDocument: RawDocument = {
	bytes: await readFile("invoice.pdf"),
	mimeType: "application/pdf",
	fileName: "invoice.pdf",
};
const health = await client.health();
console.log(health.status);
const converted = await client.convert(rawDocument);
console.log(converted.conversionStatus, converted.document.pages.length);
```

A ready server prints `ok` before conversion. The next line reports the conversion status and page count. Service calls need a running instance and are separate from the fixture-backed tests.

`baseUrl` is the service root, including any deployment prefix, without `/v1`. Construction performs no I/O.

## Check that the service is ready

Call `health()` before a batch to check the service once instead of failing on every document:

```ts
const health = await client.health();
```

`health()` calls docling-serve's `/health` route under `baseUrl` with the same headers, API key, request deadline, and GET retries as other calls. It returns a `DoclingHealth` of `{ status: "ok" }`. It accepts an optional `AbortSignal`. When the service is unreachable it throws `DoclingServeError` with reason `transport`. A non-success HTTP status throws reason `http`. A response other than status `ok` throws reason `response`. A loader does not expose `health()`, so create a `DoclingServeClient` with the same connection options.

`convert()` returns a `DoclingConversion`: the same `document`, `source`, `diagnostics`, and `provenance` that [Import Docling JSON](/docs/integrations/docling-import) describes, plus a `conversionStatus` and an optional `taskId`. The service accepts PDF, DOCX, XLSX, PPTX, and EPUB.

## Submit and resume a long job

For long conversions, submit a job and save its reference:

```ts
const job = await client.submit(rawDocument);
const saved = job.reference;
const result = await client.resume(saved).wait();
```

`DoclingJob.reference` is a plain serializable `DoclingJobReference` with the service identity and task ID. `resume(reference)` follows the task without another POST. A `DoclingJob` has three methods:

- `status()` returns a `DoclingTaskStatus` with the task ID and its state: `pending`, `started`, `success`, or `failure`.
- `result()` fetches the conversion of a finished task.
- `wait()` polls until the task finishes, then returns the conversion.

`wait()` has two deadlines. `queueTimeoutMs` bounds the time the task stays `pending` in docling-serve's queue. `jobTimeoutMs` starts when a status check first reports the task `started`, or finished, so time spent queued behind other jobs does not count against it. `maxPolls` defaults to enough checks to reach both deadlines at `pollIntervalMs`, so raising `jobTimeoutMs` alone gives a slow job more time. Set `maxPolls` only to stop earlier.

A successful task still needs a successful conversion. Aborting locally does not cancel the job on the server.

## Use the service as a loader

```ts check
import { DocumentLoaderDoclingServe } from "docture/loaders/docling";

const loader = new DocumentLoaderDoclingServe({ baseUrl: "http://127.0.0.1:5001/", mode: "async" });
```

`DocumentLoaderDoclingServeOptions` adds `mode` and default `conversion` options to the connection options. The default mode, `sync`, calls `convert()`. The `async` mode submits a job and waits for it. The loader is named `docling-serve`. It reports text capability and the `NATIVE_EVIDENCE` fact, with no line geometry or page images. Loaded documents keep the native layout, evidence, and provenance.

## Configure the connection

`DoclingServeOptions` extends `DoclingTransportOptions`, the HTTP settings:

{/* options: DoclingServeOptions */}
| Option | Default | Meaning |
| --- | --- | --- |
| `baseUrl` | required | HTTP or HTTPS service root, without credentials, query, or fragment. |
| `apiKey` | none | Sent in the `X-Api-Key` header. |
| `headers` | none | Extra request headers. |
| `fetch` | global `fetch` | Transport to use. |
| `requestTimeoutMs` | `30000` | Deadline for each HTTP request. |
| `maxRequestBytes` | `20000000` | Maximum input file size. |
| `maxResponseBytes` | `20000000` | Maximum response size, checked before JSON parsing. |
| `getRetries` | `2` | Retries for GET requests, at most `10`. |
| `getRetryDelayMs` | `250` | First backoff before a retried GET, doubled per retry with full jitter. A `Retry-After` header wins, capped at 60 seconds. |
| `jobTimeoutMs` | `300000` | Deadline for an asynchronous job, from when it starts running. |
| `convertTimeoutMs` | `jobTimeoutMs` | Deadline for the synchronous convert request, which waits for the whole conversion. |
| `queueTimeoutMs` | `jobTimeoutMs` | Deadline for an asynchronous job that is still queued. |
| `pollIntervalMs` | `250` | Delay between task status checks. |
| `maxPolls` | enough for both deadlines | Maximum task status checks. Defaults to `(queueTimeoutMs + jobTimeoutMs) / pollIntervalMs`, rounded up. |
| `importOptions` | none | `DoclingImportOptions` for the returned JSON. |

## Set conversion options

Pass `DoclingConversionOptions` to `convert()` or `submit()`, or as the loader's `conversion` option:

{/* options: DoclingConversionOptions */}
| Option | Meaning |
| --- | --- |
| `doOcr` | Run OCR in Docling. |
| `forceOcr` | Run OCR even where the file has text. |
| `doTableStructure` | Recognize table structure. |
| `tableMode` | `fast` or `accurate` table recognition. |
| `ocrLanguages` | OCR language codes. |
| `pageRange` | Inclusive first and last page. |
| `allowPartial` | Accept a partial conversion instead of rejecting it. |
| `signal` | Caller cancellation. |

Each request sends one file with its name and MIME type, and asks for in-body JSON output.

## Accept partial conversions

Partial conversions reject unless you set `allowPartial: true`. Skipped and failed conversions always reject. When you allow a partial conversion, the result keeps a `PARTIAL_CONVERSION` diagnostic with a short excerpt of the service errors, and the normalized document and converter output carry a warning. Saved `sourceMetadata` keeps `conversionStatus`, `diagnostics`, `doclingErrors`, and any `doclingTask` reference. The normalized document digest covers those warnings.

## Handle failures and retries

POST requests are never retried. A dropped submission or a sync HTTP 504 can leave the server outcome unknown. GET retries and polling are bounded. POST redirects reject, and GET redirects cannot carry credentials to another origin.

Service failures throw `DoclingServeError` with code [`DOCLING_FAILED`](/docs/resources/errors#error-catalogue). Inside an `Extractor` or `DocumentConverter`, the failure is a loader attempt with that `errorCode`, and the call raises `LOAD_FAILED` when no other loader succeeds. The error has these fields:

- `reason`, a `DoclingServeFailure`: `configuration`, `transport`, `http`, `redirect`, `response`, `task`, `expired`, `timeout`, `conversion`, or `limit`.
- `outcome`, `failed` or `unknown`. `unknown` means the server may have processed the request.
- `status`, the HTTP status when there is one, and `taskId` for job failures.

Invalid returned JSON throws `DoclingImportError` from the importer.

## Supported versions

The client implements a subset of the docling-serve 1.38.2 v1 protocol and native schema 1.10.0. Its tests run against recorded fixtures, including two real docling-serve 1.38.2 invoice responses, not a live server. The [Docling example](https://github.com/YasielCabrera/docture/tree/main/apps/examples/docling) includes local native JSON and a PDF for conversion through your own service.
