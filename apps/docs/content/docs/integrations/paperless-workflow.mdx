Extract fields from Paperless-ngx documents with your own schemas, review the planned changes, and write them back from the CLI, MCP, or your own application. [Read and search Paperless documents](/docs/integrations/paperless-read) and [Plan and apply Paperless updates](/docs/integrations/paperless-updates) describe the library behavior for Paperless 3.x with API 9 and 10.

## Set up the service account

Give a Paperless service account view permission on the documents it reads. Add change permission only for the documents your application may update, and for the targets of any document link fields it writes.

Keep the token in environment-backed application configuration. CLI and MCP arguments select configured names and cannot replace the instance, token, or mappings.

## Configure schemas and mappings

Name each schema and its field mappings once in the CLI config:

```ts check
import { defineConfig } from "@docture/cli/config";
import { jsonSchema } from "ai";

const contract = jsonSchema({
	type: "object",
	properties: { reference: { type: "string" } },
	required: ["reference"],
	additionalProperties: false,
});
const token = process.env.PAPERLESS_TOKEN;
if (token === undefined) throw new Error("Set PAPERLESS_TOKEN in the application environment.");

export default defineConfig({
	paperless: {
		connection: {
			baseUrl: process.env.PAPERLESS_URL ?? "https://paperless.example.test/",
			token,
			apiVersion: 10,
		},
		enableApply: false,
		maxResults: 20,
		schemas: {
			reference: {
				contract,
				source: { mode: "archive" },
				mappingId: "reference-fields-v1",
				fields: [{ path: ["reference"], fieldId: 7 }],
			},
		},
	},
});
```

Add your extractor, strategies, or model to the same config, as described in [CLI configuration](/docs/cli/configuration). Choose a loader for the source mode:

- For `archive`, select a PDF loader, or a Docling loader for native element and cell evidence.
- For `content`, the stored OCR text is used as is, without positioned lines. To write its uncited values, set the schema's `evidence` to `any`.

## Read and search without a model

These commands make no model calls. An omitted `--limit` defaults to the smaller of 10 and `paperless.maxResults`. An explicit limit must not exceed `paperless.maxResults`.

```sh
docture paperless read 42 --version 42
docture paperless search --query 'supplier' --limit 10
```

## Extract with a configured schema

Pass a schema name. Query extraction is bounded by the configured maximum.

```sh
docture paperless extract 42 --schema reference
docture paperless extract --query 'supplier' --limit 10 --schema reference
```

## Plan updates without writing

`plan` writes nothing to Paperless, and `extract --dry-run` also prints a plan. The plan JSON includes the exact source identity, evidence, validation, conflicts, and skip reasons.

```sh
docture paperless plan 42 --schema reference --out plan.json
docture paperless extract 42 --schema reference --dry-run
```

## Apply a saved plan

Apply one saved single-document plan at a time. The configured schema fingerprint and mapping must still match the plan. Apply checks the source identity and each current field again, and skips a field that another writer filled since planning.

```sh
docture paperless apply plan.json --schema reference --dry-run
docture paperless apply plan.json --schema reference
```

A query plan can contain several plans. Pass each selected plan object to `apply` separately. You decide whether to save partial results and when to retry. Docture keeps no receipt store and needs no approval record.

## Use Paperless from MCP

With Paperless configuration present, the [MCP server](/docs/cli/mcp) lists `paperless_read`, `paperless_search`, `paperless_extract`, and `paperless_plan`. The named schema controls the source mode, the extraction contract, and the mappings.

`paperless_apply` appears only when `paperless.enableApply` is `true`. A tool argument cannot enable it. MCP output keeps the CLI envelope, source descriptor, and evidence fields, and stdout carries only the protocol.

## Trigger extraction when documents arrive

The repository example in [`apps/examples/21-paperless`](https://github.com/YasielCabrera/docture/tree/main/apps/examples/21-paperless), `triggers.ts`, shows a webhook endpoint and queue that your application owns:

1. Create the endpoint with a configured instance, a bearer token, and a queue.
2. Configure the Paperless Document Added webhook to send the document ID and the configured instance.
3. The endpoint rejects foreign instances and invalid IDs, ignores duplicate Added deliveries, and ignores Updated events so that write-back does not trigger another run.
4. The worker checks the queued instance and reads a fresh, version-pinned source before it extracts.

A post-consume script variant reads `DOCUMENT_ID`, `PAPERLESS_INSTANCE`, `PAPERLESS_INGRESS_URL`, and `PAPERLESS_INGRESS_TOKEN` from its environment, queues the ID, and returns after HTTP 202. It does not extract inside the Paperless consumption hook.

Your application owns queue durability, deduplication retention, and retries. Importing the example module starts no server, queue, or daemon.

## Choose Docture or Paperless AI tools

Paperless provides AI suggestions and chat, and paperless-gpt provides OCR, custom field workflows, and review. Use Docture when you need TypeScript schemas you define, field evidence status, reusable validation and repair, conflict reports, chunking, and evaluation across document sources.

The repository example uses a local authenticated mock server and deterministic providers. Running against a live Paperless instance, Docling, or a model needs your own credentials.
