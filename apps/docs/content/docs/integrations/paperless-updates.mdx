---
title: Plan and apply Paperless updates
description: Plan and explicitly apply typed field changes while preserving existing Paperless values.
---

`docture/sinks/paperless` exports `PaperlessSink`, `paperlessSink`, `PaperlessError`, `PaperlessProvenance`, `PaperlessFieldType`, `PaperlessValue`, `PaperlessCustomFieldDefinition`, `PaperlessSinkOptions`, `PaperlessFieldMapping`, `PaperlessEvidencePolicy`, `PaperlessPlanInput`, `PaperlessPlan`, `PaperlessPlanExtraction`, `PaperlessPlanIssue`, `PaperlessPlannedSkip`, `PaperlessOperation`, `PaperlessOperationOutcome` and `PaperlessApplyResult`.

The entry uses fetch only. It imports shared transport and validation helpers without importing the source facade, models, PDF engines or a store. Construction performs no network requests.

```ts
import { PaperlessSink } from "docture/sinks/paperless";

function configuredSink(baseUrl: string, token: string) {
	return new PaperlessSink({
		baseUrl,
		token,
		apiVersion: 10,
		fields: [{ path: ["invoiceNumber"], fieldId: 7 }],
		tagIds: [3],
		auditNote: "Docture extraction",
	});
}
```

`PaperlessSinkOptions` extends the connection options of the [source entry](/docs/integrations/paperless-read). Each field mapping contains a segment array and an existing native field ID. A literal dotted key is one segment, such as `["total.net"]`. Duplicate paths, field IDs or tag IDs reject. Tags and custom fields must already exist. The sink does not create taxonomy.

`PaperlessEvidencePolicy` defaults to `verified`. `cited` also permits `cited-unverified`. `any` explicitly permits uncited or derived values. A field mapping can set its own policy. A saved plan cannot replace constructor configuration. Evidence status describes the extraction's evidence and does not prove semantic correctness.

`plan` accepts exact source provenance, an extraction result, `schemaId`, `mappingId` and an optional `extractionId`. It reads current source identity, metadata and native definitions without mutating Paperless. Validation failures, conflicts affecting mapped paths, missing definitions, permission failures and rejected evidence become `blocked` issues. Existing nonempty fields and empty extracted values have explicit `skipped` reasons.

The plan records native operations, evidence status, source digest, root and selected file identity, schema and mapping identity, validation and conflict data, and limitations. Its stable note marker binds the source, extraction data and current sink configuration. A caller-supplied extraction ID does not replace that binding. The marker identifies an extraction for note deduplication. It is not an approval token.

| Native type | Proposed value |
| --- | --- |
| `string` | Text of at most 128 Unicode characters. |
| `longtext` | Text within the plan byte limit. |
| `url` | An absolute URI without whitespace. |
| `date` | A real `YYYY-MM-DD` date. |
| `boolean` | A JSON boolean. |
| `integer` | A signed 32-bit integer. |
| `float` | A finite JSON number. |
| `monetary` | A value with at most two decimal places, or a native currency string such as `USD12.30`. Numeric inputs become native strings. |
| `documentlink` | Distinct existing root document IDs, excluding the source ID. |
| `select` | An existing option ID from the field definition. |

Missing and null fields are empty. Blank strings are empty for text, date, URL, monetary and select fields. An empty documentlink array is empty. `0` and `false` are present values and remain untouched.

Documentlinks have native reciprocal effects. Planning requires confirmed change permission on each target. A target's reverse field must be empty or already contain the source ID. Apply checks these conditions again before submission. The native server still has a read/write race. A target can change after its last check.

`inspect(unknownSavedPlan)` validates bounded JSON, supported versions, allowed operations, configured mappings and evidence policy. It performs no network calls. Unknown keys, duplicate operations and mismatched configuration reject. The defaults are 1,000 operations and a 4 MiB serialized plan, with additional traversal bounds.

`apply(plan)` is an explicit caller operation. It needs no approval record, confirmation hash or durable receipt. It checks the selected source digest again, re-reads each field before writing, and skips any field that became nonempty. It uses native targeted `modify_custom_fields` with an empty removal array, and additive `add_tag`. Unrelated fields and existing tags remain present.

Before a note POST, apply reads notes and checks the stable extraction marker. It reconciles uncertain responses by reading the field, tag or note marker again. A disconnect, timeout, 5xx response, native 400 after mutation, or an error-shaped note response cannot prove that nothing changed. Apply never blindly retries a note POST. Repeated explicit calls inspect current state again.

`PaperlessApplyResult` contains per-operation `applied`, `skipped`, `failed` or `unknown` outcomes with reasons. The `skipped` property retains skips found during planning. `partial` preserves confirmed work when another operation fails or remains uncertain. `cancelled` preserves completed outcomes, marks a possibly submitted operation unknown and skips later work.

The pinned Paperless-ngx 3.3.4 metadata methods return `OK` after updating native values and queue background indexing without a task ID. Metadata read-back does not prove indexing completion. Paperless offers neither a multi-operation transaction nor conditional field writes. Stable markers support retry reconciliation but cannot guarantee exactly-once concurrent notes. The caller owns result persistence, retry policy and retention.

Run `pnpm --dir apps/examples exec tsx 21-paperless/index.ts` for source reads, schema extraction, a partial apply, co-writer preservation, additive tags, one marked note and a repeated apply against a local mock server.
