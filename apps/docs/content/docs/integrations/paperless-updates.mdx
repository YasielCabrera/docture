---
title: Plan and apply Paperless updates
description: Plan and explicitly apply typed field changes while preserving existing Paperless values.
type: how-to
---

`PaperlessSink` turns an extraction result into a plan of Paperless custom field, tag, and note changes, and applies that plan when you call `apply`. Import it from `docture/sinks/paperless`. Existing nonempty field values and existing tags are never overwritten or removed. To read documents first, see [Read and search Paperless documents](/docs/integrations/paperless-read).

## Configure the sink

```ts check
import { PaperlessSink } from "docture/sinks/paperless";

function configuredSink(baseUrl: string, token: string) {
	return new PaperlessSink({
		baseUrl,
		token,
		apiVersion: 10,
		fields: [{ path: ["invoiceNumber"], fieldId: 7 }],
		tagIds: [3],
		auditNote: "Docture extraction",
	});
}
```

`paperlessSink(options)` returns the same object. The sink uses `fetch` only, and construction makes no network request. `PaperlessSinkOptions` extends the connection options of `PaperlessSource`:

{/* options: PaperlessSinkOptions */}
| Option | Default | Meaning |
| --- | --- | --- |
| `baseUrl` | required | HTTP or HTTPS service root. |
| `apiVersion` | required | `9` or `10`. |
| `token` | none | API token. |
| `headers` | none | Extra request headers. |
| `fetch` | global `fetch` | Transport to use. |
| `timeoutMs` | `30000` | Deadline for each request. |
| `maxResponseBytes` | 32 MiB | Maximum streamed response size. |
| `fields` | required | `PaperlessFieldMapping` entries from extraction paths to existing custom field IDs. |
| `tagIds` | none | Existing tags to add. |
| `auditNote` | none | Text of a note to add once per extraction. |
| `evidence` | `verified` | Default `PaperlessEvidencePolicy` for every field. |
| `maxOperations` | `1000` | Maximum operations in a plan. |
| `maxPlanBytes` | 4 MiB | Maximum serialized plan size. |

## Map extraction paths to fields

Each `PaperlessFieldMapping` has a `path` array, an existing `fieldId`, and an optional `evidence` policy. Each array item is one path segment, so a literal dotted key is one segment, such as `["total.net"]`. Duplicate paths, field IDs, or tag IDs reject. Tags and custom fields must already exist, because the sink never creates them.

The `PaperlessEvidencePolicy` decides which values the sink may write:

- `verified`, the default, accepts only values whose citations were verified.
- `cited` also accepts `cited-unverified` values.
- `any` also accepts uncited or derived values.

A saved plan cannot replace the constructor's policy. Evidence status describes the extraction's citations. It does not prove the value is correct.

## Create a plan

`plan(input)` takes a `PaperlessPlanInput`: the exact source `provenance` from `PaperlessSource.read`, the `extraction` result, a `schemaId`, a `mappingId`, and an optional `extractionId`. It reads the current source identity, metadata, and field definitions, and changes nothing in Paperless.

The returned `PaperlessPlan` contains:

- `operations`, each a `PaperlessOperation` that sets a field, adds a tag, or adds a note.
- `blocked`, a `PaperlessPlanIssue` for each validation failure, conflict on a mapped path, missing definition, permission failure, or rejected evidence.
- `skipped`, a `PaperlessPlannedSkip` for each field that already has a value or whose extracted value is empty.
- The source digest, root and file identity, schema and mapping IDs, evidence status, the `PaperlessPlanExtraction` with validation and conflict data, and limitations.

The plan's `marker` binds the source, the extraction data, and the sink configuration. The sink uses it to avoid adding the same note twice. A caller-supplied `extractionId` does not replace that binding, and the marker is not an approval token.

## Check proposed values

Each proposed value must fit its `PaperlessFieldType`:

| Native type | Proposed value |
| --- | --- |
| `string` | Text of at most 128 Unicode characters. |
| `longtext` | Text within the plan byte limit. |
| `url` | An absolute URI without whitespace. |
| `date` | A real `YYYY-MM-DD` date. |
| `boolean` | A JSON boolean. |
| `integer` | A signed 32-bit integer. |
| `float` | A finite JSON number. |
| `monetary` | A value with at most two decimal places, or a native currency string such as `USD12.30`. Numbers become native strings. |
| `documentlink` | Distinct existing root document IDs, excluding the source ID. |
| `select` | An existing option ID from the field definition. |

Missing and `null` values are empty. Blank strings are empty for text, date, URL, monetary, and select fields. An empty document link array is empty. `0` and `false` are values, so a field holding them is not overwritten.

## Update document links

Paperless also updates the reverse field of each linked document. Planning requires change permission on each target. Each target's reverse field must be empty or already contain the source ID. `apply` checks these conditions again before it writes. A target can still change between that check and the write, because Paperless has no conditional write.

## Validate a saved plan

`inspect(savedPlan)` checks unknown JSON before you apply it, without network calls. It checks the size, the plan version, the allowed operations, the configured mappings, and the evidence policy. Unknown keys, duplicate operations, and a configuration mismatch reject.

## Apply a plan

`apply(plan)` writes the plan. It needs no approval record, confirmation hash, or saved receipt. Before writing, it:

1. Checks the selected source digest again.
2. Reads each field again and skips any field that now has a value.
3. Reads existing notes and skips the note if one already carries the plan's marker.

Fields are set with Paperless's targeted `modify_custom_fields` and an empty removal list. Tags are added with `add_tag`. Other fields and existing tags stay unchanged.

A disconnect, timeout, 5xx response, a 400 response after a change, or an error-shaped note response cannot prove that nothing changed. In those cases, `apply` reads the field, tag, or note marker again to find out. It never retries a note POST blindly. Calling `apply` again inspects the current state again.

## Read the apply result

`PaperlessApplyResult` has a `status`, the plan's `marker`, the `skipped` entries from planning, and one `PaperlessOperationOutcome` per operation. Each outcome is `applied`, `skipped`, `failed`, or `unknown`, with a reason.

- `complete` means every operation finished.
- `partial` keeps the confirmed work when another operation failed or stayed uncertain.
- `cancelled` keeps finished outcomes, marks an operation that may have been sent as `unknown`, and skips the rest.

Your application owns saving results, retries, and retention.

## Know what Paperless guarantees

Paperless-ngx 3.3.4 returns `OK` after it updates values and queues search indexing without a task ID, so reading metadata back does not prove indexing finished. Paperless offers no multi-operation transaction and no conditional field write. The marker supports reconciling retries, but cannot guarantee exactly one note when several writers run at once.

Failures throw `PaperlessError`, as described in [Read and search Paperless documents](/docs/integrations/paperless-read#handle-errors). `PaperlessProvenance`, `PaperlessValue`, and `PaperlessCustomFieldDefinition` are the same types the source entry exports.
