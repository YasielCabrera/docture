Testing uses three public entries. `docture/testing/doubles` needs no peer.
`docture/testing/fixtures` needs PDFKit. `docture/testing/conformance` needs PDFKit and
Vitest 3 or newer because it generates PDFs and registers tests.

## Generated invoices

Import from `docture/testing/fixtures`.

```sh
npm install --save-dev docture pdfkit@0.19.1
```

```ts
buildInvoiceData(options?: InvoiceOptions): SyntheticInvoice
makeInvoicePdf(options?: InvoiceOptions): Promise<SyntheticDocument<SyntheticInvoice>>
formatMoney(value: number): string
makeRichDocumentPdf(): Promise<SyntheticDocument<RichDocumentExpected>>
richDocumentExpected(): RichDocumentExpected
```

`InvoiceOptions` has `seed`, `lineItemCount`, and `textless`. Defaults are seed `1`, five
line items, and a normal text-layer PDF. A seed reproduces the same values. `textless`
creates a PDF without text for scan behavior tests.

`SyntheticDocument<T>` contains PDF `bytes`, `expected` data, and actual `pageCount`.
`SyntheticInvoice` contains invoice number, dates, currency, seller, buyer, line items,
subtotal, tax rate, tax, and total. `SyntheticLineItem` contains description, quantity,
unit price, and amount.

`formatMoney()` returns a two-decimal, US-formatted string. `buildInvoiceData()` and
`formatMoney()` are synchronous. `makeInvoicePdf()` is asynchronous and rejects if PDF
generation fails.

`makeRichDocumentPdf()` produces a deterministic two-page fixture with multiple columns,
typography, a list, table, link, code block, and embedded raster image.
`RichDocumentExpected` contains each source string and structural expectation.

## Conversion corpus

Import from `docture/testing/fixtures`.

```ts
conversionCorpus: readonly ConversionCase[]
```

`conversionCorpus` holds loaded documents that reproduce known layout cases: page numbers
outside the margin band, a form section under a table, a centred group header, a two-page
running header, unrelated text-only tables across a page break, and a contents entry at a
page break. Each `ConversionCase` has an `id`, a `description` of the layout and the
expected behaviour, a `loaded` document, and the `checks` its conversion should pass.
Check ids start with the case id.

Convert `loaded` with `DocumentConverter` and grade the result with `checkConversion` from
`@docture/eval/conversion`. The cases are already loaded, so converting them needs no PDF loader. Some cases describe
behaviour that the converter does not implement yet, and their checks fail until it does.

## Test doubles

Import from `docture/testing/doubles`.

```sh
npm install --save-dev docture
```

```ts
loadedDocument(
  pageTexts: readonly string[],
  options?: { loader?: string; geometry?: boolean },
): LoadedDocument

inMemoryLoader(document: LoadedDocument): DocumentLoader
fixedStrategy(name: string, data: unknown): ExtractionStrategy
failingStrategy(name: string, message = "strategy failed"): ExtractionStrategy
```

`loadedDocument()` creates A4-sized pages and geometry by default. The default loader name
is `in-memory`. `inMemoryLoader()` accepts every media type and returns the supplied
document. `fixedStrategy()` returns fixed data after checking the abort signal.
`failingStrategy()` always throws the configured message.

## Conformance suites

Import from `docture/testing/conformance`. Add the peer for the adapter under test.

```sh
npm install --save-dev docture pdfkit@0.19.1 'vitest@>=3'
```

```ts
describeLoaderConformance(options: LoaderConformanceOptions): void
describeRasterizerConformance(options: RasterizerConformanceOptions): void
```

`LoaderConformanceOptions` requires a suite `name` and a fresh loader `create` function.
Its optional `fixtures` selects the documents the suite loads, and defaults to
`pdfFixtures`. Its optional `skip` object can skip geometry, images, multi-page, or scanned
checks when a loader does not claim that behavior.

`RasterizerConformanceOptions` requires a suite `name` and fresh rasterizer `create`
function. Its optional `fixtures` defaults to `pdfFixtures`, and its optional `format`
selects an advertised output format to check, `"png"` by default. The suite checks that
the rendered bytes carry that format's signature.

### Fixture profiles

A `ConformanceFixtures` profile names a media type and supplies seeded documents. Each
`ConformanceDocument` has `bytes`, `mimeType`, the `expectedText` a text-reading loader
must find, and optionally its `pageCount` and expected `form`. When a document has no
`expectedText`, as with `pngFixtures`, the content and geometry checks skip, and the reuse
checks compare rendered page images instead of text.

| Profile | Media type | Real page size | Multi-page | Scanned | Invalid input |
|---|---|---|---|---|---|
| `pdfFixtures` | `application/pdf` | yes | yes | yes | yes |
| `textFixtures` | `text/plain` | no | yes, form-feed pages | no | no |
| `pngFixtures` | `image/png` | yes | no | blank page | yes |

```ts
import { DocumentLoaderData } from "docture";
import { describeLoaderConformance, textFixtures } from "docture/testing/conformance";

describeLoaderConformance({
  name: "DocumentLoaderData",
  create: () => new DocumentLoaderData(),
  fixtures: textFixtures,
});
```

The suites report a check as skipped when the profile has no document for it or the
loader's capabilities rule it out. Positive page dimensions are required only from a
profile with a real page size, and a text profile never treats text as invalid input.
Abort, instance reuse, and disposal checks run for every profile. A loader without text
must return different first-page images for different documents.

The functions register Vitest suites and return `void`. Test failures are reported by
Vitest. Create functions may return a component or a promise.

`ConversionCaseCheck` is the structural check shape on a fixture case. Pass fixture checks to `checkConversion` from `@docture/eval/conversion`.
